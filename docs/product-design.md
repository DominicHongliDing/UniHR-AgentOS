# UniHR 的产品设计：从一句要求到可用的材料

[返回项目](../README.md) · [核心案例：培训表格与提醒通知](cases/training-follow-up.md) · [完整 PRD（立项评审稿）](PRD.md)

## 问题从哪里来

在高校从事人事、行政和国际交流工作时，我常要查政策、核对表格、准备通知。即使一段文字已经写好，仍要确认事实、附件和格式，才能进入下一步工作。这些经历和与经办同事的交流，是 UniHR 的需求来源。

我把产品目标放在可交付材料上：帮助经办人完成一项具体任务，并方便核对和继续修改。现阶段是个人 Demo，尚未取得组织试用后的任务用时与返工基线。

## 服务对象与优先任务

首要对象是高校人事和行政经办人员。使用者要完成政策查询、材料对照、文稿和表格处理；审核人员确认正式口径；制度维护人负责来源版本。

| 用户任务 | 希望减少的负担 | 当前优先设计 |
|---|---|---|
| 查制度及适用条件 | 找原文、核对版本、解释差异 | 回答附来源，条件不清时说明缺口 |
| 整理业务表格 | 重复核对、计算、处理异常 | 确认口径、实际计算、交付可编辑表格 |
| 准备通知及附件 | 在多个工具之间重复搬运内容 | 沿用确认事实，核对正文与附件一致性 |
| 接着修改已有结果 | 重新解释对象和限制 | 保留任务材料和版本，只处理指定修改 |

上述任务的真实频次与节省时间仍需试用确认。本轮用“培训完成情况表和提醒通知”把一个组合任务讲透，不把功能清单当作需求优先级的证明。

## 为什么采用任务工作台

聊天工具适合起草与解释；模板适合固定格式；电子表格适合明确计算。UniHR 尝试把它们组织在同一任务中，保留材料、口径、结果和修改要求，减少用户重复交代与搬运内容。

简单文本任务直接处理。需要多份材料或多种工具时，再组织步骤；文件是否可用、政策是否有依据，分别检查。正式发送、录用与定薪由授权人员决定。

首轮验证先围绕用户主动提供的材料展开。系统接入和更多模板应依据实际重复工作决定，避免在核心交付尚未验证时继续扩大范围。

## 一项核心需求怎样落到设计

[培训跟进案例](cases/training-follow-up.md)从一句自然语言要求开始，明确统计人数、完成率口径、未知项和通知对象，再定义输入、当前任务信息、处理步骤、AI 输出和用户看到的内容。

这个拆法用于检查每项功能是否服务于用户任务。例如，RAG 解决需要核对制度出处的问题；表格工具负责计算；任务状态帮助接续工作；Word 工具负责真正生成文件。每项能力都需要能说明它帮用户省去了哪一步。

## 异常与人工确认

关键歧义需要用户确认，已经清楚的普通任务不逐步审批。空白字段单列未知，来源冲突展示差异，文件失败保留可用部分。界面需要明确哪些材料可用、哪些仍未完成，以及下一步能做什么。

经办人确认材料和业务口径，审核人确认正式用途，制度负责人维护来源。AI 可以提出解释与处理建议，不能把这些建议写成已获批准的事实。详细情况见[案例中的异常处理](cases/training-follow-up.md#出现问题时怎么继续)与 [PRD 第 10、11 节](PRD.md#10-异常与兜底)。

## 验证设计是否有用

先用可复算材料检查字段、人数、公式、文件内容和连续修改，再请经办人完整完成任务。将总用时拆成准备、系统处理、核对和返工，记录哪些输出被采用、哪些需要实质修改。

重点观察：用户是否需要重复解释，首次交付能否使用，文件与正文是否一致，以及失败后是否知道怎样继续。现在提供的是验收要求和样例材料，尚未有这项案例的实际模型交付及使用效果记录。
